# 设计笔记：把 HUD 塞进雷鸟 iO 的提词器通道

这些是实测踩出来的约束。改版式或换通道前请先读一遍。

## 通道选择

- 对话页（模型回复渲染的地方）由**官方宿主**控制生命期：流没有 `finish_reason`
  就结束会触发 `incomplete_stream`，页面回待机。**无法从 bridge 侧延寿**。
- 提词器是唯一可由插件驱动的**常驻页**：`LyricsTeleprompterBridge` 用 CoreConnect
  通道（`TELEPROMPTER = 0x14`）握手，支持 1 小时 lifetime 与逐行推进。
- 代价：**提词器与语音互斥**（推送前会等 `voiceAssistantBusy` 清零，且显示会话被
  提词器占用）。所以做成显式模式开关，而不是常驻后台。

## 为什么眼镜不接收语音指令

一开始想做"看着看板说话，直接切视图"。探针验证后放弃了这条路，过程记在这里，
免得以后再走一遍。

**做法**：模块把现场观测发到 bridge 的 `/v1/probe`（落盘 `.state/probe.log`），
记录语音会话起止、麦克风回调、眼镜发来的每一帧。然后戴着看板说话、按镜腿。

**结果**（看板显示的 29 秒内）：

| 观测 | 数量 |
|---|---|
| `VOICE_ASSISTANT` 业务帧 | 0（正常对话时每轮都有 `0xa1`/`0x1`/`0x36` 三帧） |
| `onAssistantStartWorkflow`（语音轮次启动） | 0 |

也就是说，提词器在屏时，**眼镜固件本身不打开语音通道**，唤醒词完全不起作用。
拦截点不在 App 层——连"提前拦截唤醒"的地方都没有。这不是实现问题，改不了。

顺带否定的几个想法：

- **"唤醒即暂停看板"**：做不到，见上。就算能做到，也会被旁边的人反复误唤醒。
- **眼镜麦克风 → 手机转发**：眼镜的麦克风是给官方语音链路用的，同一条 BLE 音频
  通道，提词器在屏时不开放。
- **手机录音 + 本地识别**：技术上可行（SenseVoice int8，5.6 秒音频约 180ms，
  完全离线），但需要按一下镜腿、说一句、等识别，步骤比直接滚一下滚轮多。
  做出来试过后，用户选择了滚轮，所以**这条路的代码没有进仓库**。

**结论**：眼镜只做显示，输入走镜腿滚轮和手机通知栏。

## 滚轮：能拿到什么，拿不到什么

眼镜滑动会向手机发 `0x08` 帧（`MSG_PROGRESS_UPDATE`，action=1），带 `pageOffset`。
关键事实：

- `pageOffset` 是**绝对位置**（字节偏移），**不是方向**。滚一下 = 36 字节 = 一行。
- 看板通常 4 行、共 150 多字节，所以从顶部滚一下就跳到 36。
- **到了边界位置就不再变化**：在顶部再上滑，`pageOffset` 还是 0。

所以方向只能推断：

```
位置变了       → 按变化方向切
位置没变，在顶 → 上一张
位置没变，在底 → 下一张
```

另外两个必须处理的坑：

- **推送后的同步帧不是手势**。推一次看板后，眼镜会回几帧带 `pageOffset` 的
  同步消息。不排除的话，每推一次就自己触发一次切换。推送后 2.5 秒内的帧只
  用来更新基线。
- **一次手势会连发好几帧**（实测一次滑动 2~6 帧）。500ms 去抖，一次手势只切一张。

## 滚轮"失灵又自己好了"的真相

修完滚轮切卡片后遇到过这样一个 bug，现象很迷惑，记下排查过程：

**现象**：刚推送完连续滑，每次都切；看板空闲几分钟后滑，手势识别到了
（`scroll_view` 有日志），但 bridge 没收到任何请求；点一次通知按钮之后，
滚轮又会恢复一段时间。

**排查**：通知按钮和滚轮走的是同一个 `switchView`，唯一的区别是调用线程——
按钮从主线程进，滚轮从 BLE 线程进。而 `switchView` 把实际工作 `post` 到 HUD
线程的 `handler` 上。`probe()` 也 post 到同一个 handler 且能发出，但 `probe`
是先入共享队列、flush 时循环清空，所以它的日志不能证明"滚轮自己那次 post"
被执行了。**最终确认：post 到 HUD 线程的任务在会话空闲数分钟后会静默丢失，
原因未深究（线程还在，轮询正常，但排队的任务不执行）。**

**修复**：`switchView` 不再 post，改为每次起一个独立短命线程直接执行。
修后实测：空闲 18 分钟后连续滑 4 次，全部在 200ms 内发出请求。

**教训**：验证一个"依赖时序"的功能，必须专门测它最不利的状态（这里就是
空闲数分钟后），刚操作完时的成功不算数——那次"验证通过"就是这个坑。

已知局限：卡片内容超过一屏时 `pageOffset` 会落在中间，这时只能靠位置变化判断
方向，在正中间滑动的首次方向可能与预期相反。当前四张卡片都不超过一屏，不受影响。

## 通知栏按钮：MIUI 会把按钮折起来

想做"不打开 App 就能切视图"的按钮，能选的很少：

| 形式 | 能不能做 | 原因 |
|---|---|---|
| 常驻通知 + 动作按钮 | ✅ | 不用改清单 |
| 桌面小组件 / 快捷设置磁贴 | ❌ | 要在 `AndroidManifest.xml` 里声明 receiver / TileService，当前构建流程只改 smali |
| 悬浮在其他 App 上的按钮 | ❌ | App 没有 `SYSTEM_ALERT_WINDOW` 权限，同样要改清单 |

两个实测结论：

- **按钮需要一个新的广播接收器，但不能加清单项**。解法是把 `PendingIntent`
  指向宿主 App **已经声明**的接收器（share 插件的 `SharePlusPendingIntent`），
  再在它的 `onReceive` 开头注入一行调用。接收器是 `exported=false` 也没关系，
  `PendingIntent` 走的是 App 自己的身份。
- **MIUI 默认把动作按钮折叠**，通知只显示标题和一行文字。所以"点通知本体 =
  下一张"是必须保留的路径，不能只靠按钮。

渠道重要度要用 `IMPORTANCE_DEFAULT`：用 `LOW` 时通知可能被归到不显眼的位置。

## 滚轮和按钮都能把看板叫出来

`GET /v1/hud` 在 HUD 模式关闭时返回 503。如果不处理，通知按钮在模式关闭时
点了没反应。所以模块切视图前先 `POST /v1/hud/on`——不说话也能把看板拉起来。

## 构建迭代很慢，除非缓存

完整构建要反汇编 7 个 DEX、逐个注入、重新汇编，约 15 分钟，再加下载安装 444MB。
但我们自己的代码**全部编进追加的那一个 DEX**（`classes8.dex`，约 350KB）。

把已打补丁的官方 DEX 缓存下来，只重编追加 DEX、替换进 APK、重签，一轮可以
降到 1~2 分钟。配合 `adb install -r` 就不用每次下载。

## 踩过的构建坑

- **注入点必须在 `.registers` 之后**。把 `invoke-static` 插在方法签名后面、
  `.registers` 前面，smali 汇编会失败。正确位置是 `.registers N` 那一行的下一行。
- **官方 APK 的版本号要和补丁对得上**。`1.0.20` 的 `classes5.dex` 汇编时报
  `Unsigned short value out of range: 65536`（方法数超限），`1.0.25` 才能过。
  从应用商店导出的 APK 文件名往往看不出版本，先用
  `aapt dump badging <apk> | head -1` 确认 `versionName`。
- **不要覆盖 LovelyRayNeoio `tools/lib` 下的 jar**。误下成 404 页面会让
  baksmali/smali 全部失效，只能从 `lib_bak` 恢复。

## 探针日志里的"重启循环"（原因未确认）

有一次装完新版后的约 65 秒里，探针日志中的启动标记出现了 20 次，像是 App
被反复拉起。当时怀疑是模块在 `start()` 里启动了前台服务导致的，但后来
**带着同样的前台服务启动代码重装，启动标记只出现 1 次**，所以这个怀疑不成立。
更可能是刚安装完那几分钟安装器或系统的行为，但没有进一步确认。

如果再遇到：先看它是装完之后才有、还是运行中也会出现，再决定要不要查。

## 文本排版（提词器页）

以 `MAX_LINE_HALF_WIDTH = 34` 为单行上限，按“汉字=2、ASCII=1”估宽：

| 规则 | 原因 |
|---|---|
| 右列与左列之间不要有多个连续空格以外的东西 | 空格是渲染层的换行点，长内容会在空格处断行 |
| 右列尽量用 ASCII（`>` `.` `!`） | `▶`、`·` 等符号宽度不确定；emoji（`☀🌙🌡`）无字形 |
| 时长压缩（秒/分/时+分） | `1分59秒` 变长会把整行撑爆；固定长度才能保持对齐 |
| 方块字符按 2.5~3 单位估 | `█/░` 比汉字更宽，6 格 + 百分比曾导致换行；最终用 10 格且不带百分比 |
| 右边界统一 33 | 34 是理论上限，实际渲染在 34 附近会换行；33 稳定 |
| 标题行要避免 | `buildCustomNoteManuscript` 会自动加 `[提词] 标题` 首行；HUD 需要无标题变体 |

## 对齐调试法

1. 先让 `.state/hud` 输出纯文本，本地 `curl` 数宽度；
2. 真机上每次只调 1~2 格，记录哪一行先断；
3. 三行用同一个右边界后，若仍有 1 格偏差，多半是 `°`/全角冒号等字符的度量差异，
   单独给该行补空格即可。

## 电量

- 标准 `BluetoothDevice.getBatteryLevel()` 是系统 API（公开 SDK 无此方法），
  反射调用在实机上返回 `0`，即设备没有可用的 Battery Service 数据。
- Turbo-IO 证明可以用 OTA 通道的只读 `type=2` 帧读 `BatteryLevel`，但需要移植
  `OtaFrame`/`NavReflect`/`HostAbi`/`NativeTransfer.otaConnection`（300+ 行），
  且与提词器共用蓝牙链路有冲突风险。**未采用**。

## 飞书

- 未读数：开放平台服务端**没有**未读接口（只有客户端小程序 `getChatInfo().badge`）。
- 可行替代：`lark-cli task +get-my-tasks --complete=false --page-all` 的未完成总数
  （含“来自会话”任务），与飞书“我负责的”数字一致。
- 若只想列手写待办，过滤 `summary` 含“来自会话”的条目（本项目“我的待办”语音指令如此）。
- **`lark-cli` 每次调用要起一个进程，实测约 0.94 秒。** 把它放在 `/v1/hud` 的请求
  路径里，缓存失效那一次轮询就会卡 1 秒以上——表现为“隔很久第一次切看板很慢”，
  很容易误判成蓝牙握手慢。现在这些数据由后台每分钟预取，请求路径只读内存，
  实测 `/v1/hud` 从约 1000ms 降到约 2ms。天气和余额同理（过期先返回旧值、后台刷新）。
- **`lark-cli minutes +detail` 会把带说话人名和时间戳的逐字稿写进 cwd 下的一个文件**，
  并在返回 JSON 的 `data.minutes[0].artifacts.transcript_file` 里给出路径。
  在这个仓库目录里跑它之后 `git add -A`，会议原文就会进公开仓库。
  `.gitignore` 已挡住 `minutes/`。归档脚本在一个独立临时目录里运行它，见
  [`archive/README.md`](../archive/README.md)。

## 两把 token

App 的 Key 栏只有一个，而它同时承担“轮询看板”和“语音问答”两件事。语音问答走
`/v1/chat/completions`，这个接口能创建和完结飞书待办。所以给手机的那把 token
不能既满足语音、又不给写权限——只能二选一：

| | display | full |
|---|---|---|
| 看板、切视图、开关 | ✓ | ✓ |
| 语音问答、建/完结待办、完整会话快照 | ✗（403） | ✓ |
| 代价 | 语音口令失效，改用滚轮和通知按钮 | 手机丢了等于丢了建待办的权限 |

本仓库推荐 display：眼镜本来就不接收语音指令，开关看板有滚轮和通知按钮两条路。

## 移植到其他眼镜（仅记录，未实现）

本项目只验证过雷鸟 iO。若要换设备，需要替换的是**眼镜侧通道**，数据侧可以保留：

| 层 | 是否可复用 | 说明 |
|---|---|---|
| `bridge`（状态模型、`/v1/hud` 文本、天气/余额/待办） | ✅ | 纯文本输出，任何能显示文本的设备都能接 |
| 版式经验（宽度、ASCII 符号、时长压缩） | ✅ | 与具体设备无关的排版原则 |
| 提词器推送（`hud-module` + LovelyRayNeoio） | ❌ | 依赖 iO 的 CoreConnect 0x14 通道与雷鸟 AI App |
| 设备配对 / 常驻显示 | ❌ | X3 系列跑独立系统（如 Everyday 这类原生 App），Air 系列没有屏显能力，其他品牌各有 SDK |

换句话说：**HUD 的数据和排版可以搬，眼镜端的接入要按目标设备重写**。

- bridge 对 SQLite 只读；ZCode 升级改表结构时先跑 `/health` 与 `/v1/state` 自检。
- `session_input` 里 `sendText` / `backgroundNotification` 是消息流，不是“等你确认”，
  需要过滤 + 15 秒停留门槛，否则会误报。
